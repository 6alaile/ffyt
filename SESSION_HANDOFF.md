# FFYT — Sub-Composition Fix: Session Handoff

## Status

The clip + voiceover pipeline was rendering correctly (text and audio) but **stock video clips were missing** in the rendered output (flat dark frames behind the text). This session identified the actual root cause — not the `<template>` wrapper, but a stray `<template>` reference inside a comment block in the sub-comp HTML — and the linter is now clean: `0 errors, 0 warnings`. The fix has not yet been verified end-to-end in CI; the local lint pass is clean and the `hyperframes inspect` step finds one pre-existing `canvas_overflow` info (text from scene 2's body extending 89px past the bottom of the canvas) that is unrelated to this fix.

## What was wrong

Three compounding bugs in the HTML emitted by `scripts/generate_html.py`:

1. **Sub-comps used the wrong HyperFrames shape.** The skill (`C:\Users\PC\.claude\skills\hyperframes\SKILL.md:168`) is explicit: a file loaded via `data-composition-src` must have a `data-composition-id` and `data-width`/`data-height` on its root element, and the linter enforces this with `root_missing_composition_id` and `root_missing_dimensions` errors. The previous code put `id="hyperframes-root" data-composition-id="scene_NN"` on a div directly in `<body>`, which the runtime couldn't mount.
2. **Asset paths inside the sub-comp used `../assets/...`**, which assumed the sub-comp was a standalone file fetched from `compositions/`. When the runtime injects sub-comp content into the parent document, asset URLs are resolved against the parent (`hf_input/`), so `../` walked out of the project entirely and every video src 404'd.
3. **A multi-line comment in `build_scene_html()` mentioned `<template>` and `</template>` as part of an explanation.** The hyperframes linter's `buildLintContext` (cli.js:48281) does:
   ```js
   const templateMatch = source.match(/<template[^>]*>([\s\S]*)<\/template>/i);
   if (templateMatch?.[1]) source = templateMatch[1];
   ```
   …which is a global regex — any `<template>` reference in the file (even inside a comment) corrupts the source the linter sees. The previous session blamed the `<template>` *wrapper element* (which isn't actually wrong, per `docs/compositions.md` and `registry/examples/add-block.md` — the wrapper is only used by registry blocks). The real culprit was the comment text.

The text rendered (it's all in the parent DOM), the audio worked (its path was already parent-relative), but the videos silently failed.

## What was changed in this session

All changes are in `scripts/generate_html.py`. The composition files (`composition.html`, `compositions/scene_*.html`) are regenerated by the script and are not hand-edited.

### 1. Removed the offending comment

**`build_scene_html()`** (around line 565) had a multi-line `<!-- ... -->` block in the body that mentioned `<template>` and `</template>` to explain why no wrapper was used. The linter's regex was matching against this text and stripping the body down to nothing, after which `findRootTag` couldn't find a div with `data-composition-id`. The fix was to delete the comment entirely. The body now opens directly with the root `<div>`.

### 2. Inlined `@font-face` declarations into each sub-comp's `<style>`

The previous session left a `<link rel="stylesheet" href="assets/fonts/fonts.css" />` in the sub-comp `<head>`, expecting that would register the font families. It doesn't — the linter's `extractFontFaceFamilies` (cli.js:50721) only scans the file's own inline `<style>` blocks for `@font-face` rules; external stylesheets are not counted. So `font_family_without_font_face` warnings fired for every sub-comp.

The fix was to add 5 inline `@font-face` rules at the top of the sub-comp's `<style>`, covering the latin face for each font the scene uses (Anton, Manrope 350 + 400, JetBrains Mono, Arial Narrow). The `src: url(...)` paths use the actual filenames in `assets/fonts/`:

```css
@font-face { font-family: "Anton"; font-weight:400; src: url("assets/fonts/1Ptgg87LROyAm3Kz-C8.woff2") format("woff2"); font-display: block; }
@font-face { font-family: "Manrope"; font-weight:350; src: url("assets/fonts/xn7gYHE41ni1AdIRggexSg.woff2") format("woff2"); font-display: block; }
@font-face { font-family: "Manrope"; font-weight:400; src: url("assets/fonts/xn7gYHE41ni1AdIRggexSg.woff2") format("woff2"); font-display: block; }
@font-face { font-family: "JetBrains Mono"; font-weight:400; src: url("assets/fonts/tDbv2o-flEEny0FZhsfKu5WU4zr3E_BX0PnT8RD8yKwBNntkaToggR7BYRbKPxDcwg.woff2") format("woff2"); font-display: block; }
@font-face { font-family: "Arial Narrow"; font-weight:400; src: url("assets/fonts/tss0ApVBdCYD5Q7hcxTE1ArZ0bbwiXw.woff2") format("woff2"); font-display: block; }
```

The `<link rel="stylesheet" href="assets/fonts/fonts.css" />` was kept — it's not counted by the linter but is still useful for the runtime renderer.

### 3. Fixed the video `id` to include the scene index

**`build_scene_html()`** previously hardcoded `id="vid-scene1"` for every sub-comp's `<video>` element. The linter has a `media_missing_id` rule that fires when a `<video>` has `data-start` but no `id` (the renderer uses the id to discover media). The probe test in this session showed all 8 sub-comps would have hit `media_missing_id` once the comment issue was fixed, because they all hardcoded the same id and the linter may also be checking uniqueness — and more importantly, every sub-comp's video was missing a proper id. Changed to `id="vid-scene{idx:02d}"` so each sub-comp has a unique id matching its scene number (`vid-scene01`, `vid-scene02`, etc.). The `data-scene` attribute was updated to match.

### 4. No other structural changes

`build_scene_html()` is still emitting a root `<div>` with `data-composition-id` + `data-width`/`data-height` directly in `<body>` — no `<template>` wrapper, no `<div id="hyperframes-root">` wrapper. The sub-comp timeline registration (`window.__timelines["scene_NN"] = { paused: true }`) is still in a plain `<script>` block at the end of the root div, not on `DOMContentLoaded`. `clip_src(scene_id)` still returns `assets/clips/{id}_processed.mp4` (no `../`) and is used as-is. `build_parent_html()` was not touched in this session.

## What I tried that didn't work (so you don't redo it)

- **`<template id="scene_NN-template">` wrapper around the sub-comp content.** The skill's `SKILL.md:168-189` example shows this pattern (which is what registry blocks like `data-chart` use), and the previous session implemented it in the first round. The linter rejected it with `root_missing_composition_id` and `root_missing_dimensions` because the linter validates the file as an entry composition and looks for the `data-composition-id` / `data-width` / `data-height` on the file's root DOM element, not on a `<template>`'s child. The fix was to drop the `<template>` and put the root `<div>` directly in `<body>`. But this is correct per `docs/compositions.md` and `registry/examples/add-block.md` — the wrapper is a registry-block convention, not a sub-comp requirement. The linter accepts the simple div-in-body shape.
- **`<link rel="stylesheet" href="../assets/fonts/fonts.css">`.** Was in the original code. Removed in the previous session because the `../` was wrong (the sub-comp content is injected into the parent, so paths resolve against the parent). Re-adding it (without `../`, as `href="assets/fonts/fonts.css"`) is correct for runtime, but the linter still flags `font_family_without_font_face` because `extractFontFaceFamilies` doesn't read external stylesheets. The 5 inline `@font-face` rules are what silence the warning.
- **Reading the linter source to find the actual rule.** The previous session was guessing at why the linter kept complaining. The actual cause is in `buildLintContext` at cli.js:48281 — a global regex that matches `<template>...</template>` anywhere in the file, even inside comments. Removing the comment that mentioned `<template>` (and the redundant `</template>` references in the second one) was the actual fix.
